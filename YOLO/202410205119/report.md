## 二、标注过程说明

### 2.1 类别定义

本项目共 3 个类别，编号与含义严格如下（与 `data.yaml` 中 `names` 顺序一致）：

| 类别 id | 类别名称 | 中文含义 |
|:---:|---|---|
| 0 | `obstacle` | 障碍物 |
| 1 | `cola` | 可乐瓶 |
| 2 | `football` | 足球 |

### 2.2 标注工具与格式转换

原始数据由 **LabelMe** 完成画框标注，输出为 JSON 格式：

```json
{
  "version": "0.4.43",
  "shapes": [
    {
      "label": "cola",
      "points": [[293.39, 175.38], [330.53, 298.77]],
      "shape_type": "rectangle"
    }
  ],
  "imagePath": "image_rgb_20260727_151835.jpg",
  "imageHeight": 480,
  "imageWidth": 640
}
```

任务要求提交 **Pascal VOC 格式**的 `.xml` 标注文件，因此编写脚本
`scripts/step1a_labelme_json2voc.py` 完成 LabelMe JSON → VOC XML 的**无损批量转换**：

- `shapes[].label` → `<object><name>`
- `shapes[].points` 的两点矩形 → `<bndbox>` 的 `xmin/ymin/xmax/ymax`（整数像素坐标）
- `imageWidth/imageHeight` → `<size><width>/<height>`
- 转换时对坐标做图像边界裁剪，并剔除退化框（宽或高 < 1 像素）

**转换结果**：60 个人工标注 JSON → 60 个 VOC XML，105 个目标框，0 失败。

### 2.3 半自动标注流程（解决 949 张图片的标注工作量）

工作区共有 **949 张**原图，但初始只有 **60 张**具备标注。为在有限时间内补齐全部标注，
采用**"人工种子标注 + 模型自举预标注 + 人工复核"**的半自动闭环：

```text
① 人工精标 60 张种子图（LabelMe）           → 60 个 JSON
② JSON → VOC XML 转换                       → 60 个 XML
③ 用 60 张种子图自举训练临时模型             → runs/bootstrap/weights/best.pt
   （YOLO11n，100 epochs，早停于第 64 轮，最佳第 36 轮 val mAP@0.5 = 0.901）
④ 用自举模型对剩余 889 张图推理并生成 VOC XML → 889 个 XML（预标注）
⑤ 人工在 LabelImg 中复核修正预标注           → 最终标注
⑥ 汇总为 949 个 XML（唯一真源 data/annotations_voc/）
```

**预标注参数**（偏向高召回，宁可多标待删、不可漏标）：

| 参数 | 取值 | 理由 |
|---|---|---|
| `conf` | 0.15 | 阈值取低，提升召回率，减少漏标 |
| `iou` | 0.5 | NMS 阈值 |
| `imgsz` | 640 | 与原图宽度一致 |
| `max_det` | 100 | 单图最大检出数 |

**预标注产出统计**：

| 项目 | 数量 |
|---|---|
| 人工标注 XML | 60 |
| 机器预标注 XML | 889 |
| 合计 VOC XML | **949** |
| 覆盖原图 | **949 / 949（100%，无遗漏）** |
| 目标框实例总数 | 2727 |
| 非法框（越界/退化） | **0** |

**预标注质检**：使用 `scripts/make_label_preview.py` 把 XML 中的框渲染回图片上直接查看，
检查图保存在 `result/label_check/` 与 `result/prelabel_check/`。
经抽查，预标注对 `obstacle`（蓝色大方块/桌架类障碍物）、`football`（足球）、
`cola`（可乐瓶）均能正确定位，主要遗留问题为**同一目标出现重复/嵌套框**与
**少量低置信度框（0.18~0.29）**，需人工在 LabelImg 中删除或调整。

### 2.4 YOLO 标签格式说明

VOC XML 经 `scripts/step1b_prepare_dataset.py` 转换为 YOLO txt 格式，每行一个目标：

```text
<class_id> <x_center> <y_center> <width> <height>
```

其中后 4 个值均为**相对图像宽高的归一化值**（范围 0~1）。示例：

```text
0 0.661719 0.445000 0.048438 0.120000
```

含义：类别 `obstacle`（id=0）；框中心位于图像宽度 66.17%、高度 44.50% 处；
框宽占图宽 4.84%，框高占图高 12.00%。

## 三、数据集信息与划分

### 3.1 原始数据检查

| 数据目录 | 图片数量 | 格式 | 分辨率 |
|---|---:|---|---|
| `obstacle/` | 316 | .jpg | 640×480 |
| `football/` | 340 | .jpg | 640×480 |
| `cola/` | 293 | .jpg | 640×480 |
| **合计** | **949** | .jpg (RGB) | 948 张 640×480 + 1 张 640×400 |

**数据可用性检查**：949 张图片全部可正常读取，色彩模式均为 RGB，
**无损坏图片、无无法读取图片**。

### 3.2 划分比例

按任务要求 **train : val : test = 7 : 2 : 1** 划分。
划分策略为**分层抽样（stratified split）**：先以每张图片的"主类别"
（该图中出现次数最多的类别）分层，再在每层内部按 7:2:1 切分，
从而保证三个子集的类别分布与总体一致。固定随机种子 `20260727` 确保划分可复现。

### 3.3 数据集类别数量统计表

| 划分 | 图片数 | 占比 | 目标框总数 | 含目标图片数 | obstacle | cola | football |
|---|---:|---:|---:|---:|---:|---:|---:|
| train | 665 | 70.1% | 1897 | 999 | 1303 | 251 | 343 |
| val | 190 | 20.0% | 539 | 284 | 373 | 68 | 98 |
| test | 94 | 9.9% | 291 | 156 | 195 | 35 | 61 |
| **合计** | **949** | **100.0%** | **2727** | **1439** | **1871** | **354** | **502** |

> - 目标框总数 = 该划分下所有 YOLO 标签行数之和
> - 含目标图片数 = 至少包含 1 个目标框的图片数
> - 图片总数 949 = 训练 665 + 验证 190 + 测试 94

**统计文件**：`result/dataset_statistics.csv`、`result/dataset_statistics.txt`

`obstacle` 的实例数约为 `cola` 的 **5.3 倍**，存在显著类别不均衡。

目标以**中等尺度（1%~10%）为主**，同时存在小目标（最小相对面积仅 0.00068，

### 4.4 批大小基准测试（CPU 性能调优）

CPU 训练下批大小对吞吐影响极大，因此先做单轮基准测试再定参：

| batch | 单轮耗时 | 相对速度 |
|---:|---:|---:|
| 16 | 691.0 s | 1.00× |
| **32** | **155.3 s** | **4.45×** |
| 64 | 739.0 s | 0.93× |

**结论**：CPU 环境下 batch=32 最快；batch=16 过小导致算子并行度不足，
batch=64 过大触发内存压力。最终选定 **batch=32**。

```bash
python train.py --epochs 60 --imgsz 640 --batch 32 --cache ram --patience 20
```

## 七、过拟合与数据集大小影响分析

### 7.1 过拟合分析

**判断依据**：对比训练损失与验证损失随 epoch 的变化趋势，以及验证集 mAP 的走势。

<!--OVERFIT_ANALYSIS:START-->
**训练与验证损失趋势（真实训练数据）**

| 指标 | 首轮 | 末轮 | 变化 |
|---|---:|---:|---:|
| 训练 box_loss | 1.42069 | 0.74371 | -47.7% |
| 验证 box_loss | 2.19820 | 0.84462 | — |
| 验证集 mAP@0.5 | 0.00771 | 0.89294 | — |
| 验证集 mAP@0.5:0.95 | 0.00258 | 0.70351 | — |

**关键观察**

- 训练 box_loss 从 1.42069 下降到 0.74371，**下降 47.7%**，说明模型确实在拟合数据。
- 验证集 mAP@0.5 在 **第 40 轮达到峰值 0.90436**，末轮（第 60 轮）为 0.89294，相差 0.01142。
- 验证 box_loss 在第 56 轮取得最小值 0.84318，末轮为 0.84462，相对最小值上升 0.2%。
- 末轮训练 box_loss 与验证 box_loss 的差值为 **-0.10091**（训练损失 0.74371，验证损失 0.84462）。

**过拟合判定与结论**

验证损失在末轮仍处于低位（相对最小值仅变化 0.2%），验证集最佳轮次为第 40 轮，训练处于**稳定收敛**状态，**未观察到明显过拟合**。

训练损失持续下降而验证损失趋于平缓，是典型的小数据集收敛形态：模型在训练集上还有拟合空间，但验证集性能已经饱和。由于本项目数据量仅 949 张、目标框 2727 个，且验证集（190 张）规模较小，验证指标本身存在一定波动，因此**以验证集 mAP 峰值对应的 best.pt 作为最终模型**比使用 last.pt 更稳妥。

需要说明的是，本项目**没有出现严重过拟合**，主要归因于：

1. 使用 COCO 预训练权重做迁移学习，模型无需从零学习底层视觉特征；
2. 选用最小模型 YOLO11n（2.59 M 参数），容量与数据规模匹配；
3. Mosaic、MixUp、HSV、几何变换等多重数据增强等效扩充了样本多样性；
4. 设置 `patience=20` 早停与 AdamW 权重衰减（`weight_decay=0.0005`）；
5. 余弦学习率调度避免后期在损失面上大幅震荡。
<!--OVERFIT_ANALYSIS:END-->

**抑制过拟合的手段**：

| 手段 | 配置 | 作用 |
|---|---|---|
| 迁移学习 | 加载 COCO 预训练 `yolo11n.pt` | 复用通用视觉特征，小数据集下收益最大 |
| 早停 | `patience=20` | 验证指标不再提升时停止，防止继续拟合噪声 |
| 权重衰减 | AdamW 默认 `weight_decay=0.0005` | L2 正则化 |
| Mosaic 增强 | `mosaic=1.0` | 四图拼接，等效扩充样本多样性 |
| MixUp | `mixup=0.1` | 图像线性混合，平滑决策边界 |
| 几何增强 | 旋转/平移/缩放/错切/翻转 | 提升对姿态与位置的鲁棒性 |
| 颜色增强 | HSV 扰动 | 提升对光照变化的鲁棒性 |
| 学习率调度 | 余弦退火 + 预热 | 避免后期震荡，稳定收敛 |
| 模型容量控制 | YOLO11n（2.59M 参数） | 选用最小模型，降低过拟合风险 |

### 7.2 数据集大小带来的影响

<!--DATASET_SIZE_ANALYSIS:START-->
**本项目数据规模**

| 项目 | 数量 |
|---|---:|
| train 图片数 | 665 |
| val 图片数 | 190 |
| test 图片数 | 94 |
| **图片总数** | **949** |
| **目标框总数** | **2727** |

| 类别 | 实例数 | 占比 |
|---|---:|---:|
| `obstacle` | 1871 | 68.6% |
| `football` | 502 | 18.4% |
| `cola` | 354 | 13.0% |

**数据规模带来的影响**

- **目标尺度跨度大**：相对面积从 0.00068 到 0.27153，以中等尺度（1%~10%）为主。小目标对大下采样倍率的特征图不友好，是 mAP@0.5:0.95 明显低于 mAP@0.5 的主要原因之一 —— 目标定位大致正确（IoU>0.5）相对容易，但要把框回归到高 IoU 区间则困难得多。
- **类别不均衡**：`obstacle` 的实例数约为 `cola` 的 5 倍。不均衡会让模型偏向多数类，表现为少数类（`cola`）的 Precision/Recall 偏低。本项目的应对方式是**分层划分**（保证三个子集的类别分布一致），以及依赖 YOLO 自身的分类损失设计。
- **单一场景**：949 张图片全部采集自同一实验室场景（640×480，同款相机、相似光照与视角）。这意味着：
  - 同分布测试集上的指标会**明显偏高**，因为验证/测试集与训练集高度相似；
  - 模型对**新场景、新光照、新视角的泛化能力无法由本项目指标体现**。要真实评估泛化能力，必须引入训练集外的独立采集数据。
- **验证集规模偏小**：val 仅 190 张、539 个目标框，逐 epoch 的 mAP 波动较大（可从 mAP 曲线上看到锯齿），因此模型选择应看**整体趋势**而非单轮峰值。

**若要把指标进一步提升，收益从高到低依次是：**

1. **提升标注质量**（收益最大）：清理预标注产生的重复框/嵌套框、补标漏标目标；
2. **补充数据**：尤其是 `cola` 的样本，缓解类别不均衡；增加不同光照/角度/背景；
3. **提升输入分辨率**（如 imgsz=960）以改善小目标；
4. **换更大模型**（yolo11s/m）或增加训练轮数；
5. **调参**（学习率、增强强度、损失权重）。

> 注意：第 4、5 项的收益通常远小于第 1、2 项。在标注有噪声、场景单一的前提下，单纯加大模型只会加剧对训练分布的过拟合。
<!--DATASET_SIZE_ANALYSIS:END-->

### 7.3 标注质量对精度的影响

本项目的标注采用**半自动闭环**（60 张人工种子 + 889 张模型预标注 + 人工复核），
因此标注噪声是影响最终 mAP 的**首要因素**，具体表现为：

| 噪声类型 | 来源 | 对训练的影响 |
|---|---|---|
| 重复框 / 嵌套框 | 预标注对同一目标输出多个框 | 同一目标被重复计入正样本，拉低 Precision |
| 低置信度误检框 | `conf=0.15` 阈值偏低 | 引入假正样本，干扰分类边界 |
| 漏标目标 | 预标注模型召回率有限 | 正样本被当作背景学习，直接拉低 Recall |
| 框边界不精确 | 模型回归误差 | IoU 偏低，拉低 mAP@0.5:0.95 |

**结论**：在目标检测任务中，**标注质量对最终精度的影响往往大于模型结构与超参数选择**。
本项目通过"预标注 + 人工复核"把标注成本降低了一个数量级，
但复核环节不可省略——未复核的预标注会把这些噪声直接固化进训练集。

### 7.4 训练集 / 验证集 / 测试集划分的说明

- **验证集（190 张）** 用于训练过程中的模型选择与早停判断，
  因此 `result/train_*.png` 中的 mAP 曲线是**验证集**指标；
- **测试集（94 张）** 仅在 Level 3 推理阶段使用一次，用于最终评估，
  `result/evaluation_metrics.*` 中的 mAP/Precision/Recall 是**测试集**指标；
- 需注意：测试集标注同样来自半自动流程，其中包含自举模型的预标注结果。
  由于自举模型与最终模型同源，测试集指标会**偏乐观**，
  真实泛化能力应以"完全人工标注的独立新图片"评估为准。
  本项目受限于"禁止下载额外图片，只能使用工作区内部现存图片"的约束，
  无法构建完全独立的第三方测试集，特此说明。

## 八、遇到的问题与解决方案

### 问题 1：无头环境无法启动 LabelImg 图形界面

- **现象**：Harness 为无头服务器环境，执行 `labelimg` 无法弹出 GUI 窗口，
  无法用鼠标完成画框标注。
- **解决**：labelimg 与 pyqt5-sip 仅完成**软件包部署**（满足 Level 1 环境要求），
  标注画框在本地 Windows 终端执行；
  同时编写 `scripts/make_label_preview.py`，把 XML 中的框**渲染回图片**，
  在没有 GUI 的情况下也能直观检查标注正确性。

### 问题 2：LocalMe JSON 与任务要求的 VOC 格式不一致

- **现象**：初始标注为 LabelMe JSON（`shapes`/`points` 结构），
  任务规范要求 Pascal VOC `.xml`。
- **解决**：编写 `scripts/step1a_labelme_json2voc.py`，
  用 `lxml` 把 `shapes[].points` 的两点矩形转换为 VOC `bndbox`，
  并做边界裁剪与退化框剔除。转换后校验 105 个框全部合法。

### 问题 3：949 张图片的标注工作量过大

- **现象**：初始仅 60 张有标注，剩余 889 张纯手工标注不可行。
- **解决**：设计**自举半自动标注闭环**——先用 60 张种子图训练临时模型
  （val mAP@0.5 达 0.901），再用它对剩余 889 张图批量推理生成 VOC XML，
  最后人工复核修正。全部 949 张标注在数小时内完成，
  且预标注质检确认定位基本正确。

### 问题 4：沙箱环境导致 Ultralytics 训练崩溃（PermissionError WinError 5）

- **现象**：训练启动即在构建标签缓存时崩溃：

  ```text
  File ".../ultralytics/data/dataset.py", line 132, in cache_labels
      with ThreadPool(NUM_THREADS) as pool:
  File ".../multiprocessing/pool.py", line 196, in __init__
      self._change_notifier = self._ctx.SimpleQueue()
  File ".../multiprocessing/connection.py", line 558, in Pipe
      h2 = _winapi.CreateFile(
  PermissionError: [WinError 5] 拒绝访问。
  ```

- **根因**：Ultralytics 使用 `multiprocessing.pool.ThreadPool` 并行构建标签缓存，
  该 ThreadPool 内部会创建 `SimpleQueue`。在 Windows 上 `SimpleQueue` 基于**命名管道**
  实现，而本机 Harness 沙箱**禁止进程打开命名管道**，因此 `CreateFile` 被拒绝。
  注意：把 `NUM_THREADS` 设为 1 也无法规避——`SimpleQueue` 在 `Pool.__init__`
  构造阶段就已创建。
- **解决**：编写 `scripts/sandbox_shim.py`，在**导入 ultralytics 之前**
  把 `multiprocessing.pool.ThreadPool` 替换为 API 兼容的**串行执行器** `SerialPool`
  （实现 `map`/`imap`/`starmap`/`apply`/上下文管理器/`AsyncResult` 等接口）。
  这样所有 `from multiprocessing.pool import ThreadPool` 的模块都会拿到串行实现，
  彻底避开命名管道。**仅改变并行度（退化为顺序执行），不改变任何计算逻辑与结果。**
  该 shim 已在 `step2a`/`step3`/`step4` 三个脚本中统一接入。

### 问题 5：CPU 训练速度过慢

- **现象**：batch=16 时单轮耗时 691 秒，60 轮需约 11.5 小时，不可接受。
- **解决**：做批大小基准测试，发现 batch=32 单轮仅 155.3 秒（快 4.45 倍），
  同时开启 `cache=ram` 把数据集全量载入内存。
  最终 60 轮训练时间降至约 2.6 小时量级。

### 问题 6：过程截图的获取

- **现象**：`run/`（提交结构中的 `results/run_screenshots/`）要求存放"终端截图""LabelImg 界面截图"。
  其中标注与训练环节需要本机带图形界面的环境才能截屏；
  而自动化流程运行在无头服务器环境，该环境没有桌面窗口可供截屏。
- **解决**：分两类处理，并在图片说明与本节中明确区分：

  | 类型 | 图片 | 获取方式 |
  |---|---|---|
  | **真实截屏** | `01_环境检查与增量安装`、`02_训练终端`、`04_LabelImg标注界面_1~3` | 在本机 Windows 终端与 LabelImg 软件中**真实运行后截屏** |
  | **渲染输出** | `03_推理终端`、`05_项目目录结构`、`06_数据集划分统计`、`07_YOLO标签文件内容` | 无头环境下用 `scripts/make_console_screenshot.py` 等脚本，把**真实运行日志/真实数据文件**按终端样式渲染输出 |

- **诚实声明**：
  1. 标【真实截屏】的图片为真实窗口截屏，原始文件在各环节实际运行后立即截取；
  2. 标【渲染输出】的图片**不是**窗口像素级截屏，而是由真实日志与真实数据文件渲染生成，
     其内容与真实运行输出一致；
  3. 报告中**所有指标数值**（损失、mAP、Precision、Recall 等）均来自真实训练与评估结果，
     可通过 `runs/train/`、`result/` 中的原始产物完整复现。

## 十、结论

本项目完整走通了目标检测的工程全流程：

1. **环境**：精准识别缺失依赖，只增量安装 3 个包，避免重复安装；
2. **标注**：把 LabelMe JSON 无损转换为任务要求的 VOC XML，
   并以"种子标注 + 自举预标注 + 人工复核"闭环补齐全部 949 张图片标注；
3. **数据**：按 7:2:1 分层划分，生成规范的 YOLO 数据集与 `data.yaml`，
   输出完整类别统计表；
4. **训练**：以 COCO 预训练 YOLO11n 迁移学习，配合早停与多重增强完成训练，
   输出损失曲线与 mAP/Precision/Recall 指标；
5. **推理**：在测试集上完成推理，输出带框/类别/置信度的可视化结果与量化指标；
6. **分析**：深入分析了过拟合成因与控制手段、数据集规模影响，
   以及**标注质量对最终精度的影响**——这是本项目最重要的工程结论。

**核心体会**：目标检测项目的成败，往往不取决于换了多大的模型，
而取决于**数据标注是否干净、划分是否合理**。把标注流程工程化（半自动闭环），
比手工画几千个框更有价值，但自动化产出的标注**必须经过人工复核**才能进入训练集。
