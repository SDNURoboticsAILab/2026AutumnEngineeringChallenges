## 三、数据检查与划分

### 1. 原始数据检查

实验室提供的三组原始图片共 **949 张**，全部为 JPEG 格式：

| 类别 | 数量 |
|---|---:|
| obstacle | 316 |
| cola | 293 |
| football | 340 |
| **合计** | **949** |

检查由 `prepare_dataset.py` 自动完成，包含两项内容：

1. **可读性检查**：用 PIL 逐张调用 `verify()`，确保没有损坏、截断或无法解码的图片；
2. **重复内容检查**：计算每张图的 **sha256 内容指纹**后分组比对。

**检查结果：损坏图片 0 张，内容完全相同的重复图片 0 组。**

> **为什么要专门查重复？** 如果内容相同的两张图分别落入训练集和验证集，就会造成**验证集泄漏**：模型在验证时"见过"这张图，指标会虚高，无法真实反映泛化能力。这里按**内容哈希**而不是文件名比对，是因为同一张图在不同目录下可能有不同的文件名。

图片尺寸为 **640×480 与 640×400 两种**（来自机器人相机的不同采集模式），格式统一为 JPEG。尺寸不统一不影响训练：YOLO 标签使用的是**归一化到 0~1 的相对坐标**，与像素分辨率无关，训练时由 dataloader 统一缩放，因此不同尺寸的图片可以混合训练。

### 2. 训练集 / 验证集 / 测试集划分

采用**按类别分层**划分：每个类别内部独立按 **80% / 10% / 10%** 切分，以保证三类在三个子集中的比例一致。乱序使用固定随机种子：

```python
SEED = 20262128003
random.Random(SEED).shuffle(sorted(items))   # 先排序再打乱，保证可复现
```

先按文件名排序再打乱，目的是让划分结果**只取决于文件集合与种子**，而不依赖操作系统返回目录项的顺序——这样在任何机器上重跑都能得到完全相同的划分。

| 类别 | train | val | test | 合计 |
|---|---:|---:|---:|---:|
| obstacle | 253 | 32 | 31 | 316 |
| cola | 234 | 29 | 30 | 293 |
| football | 272 | 34 | 34 | 340 |
| **合计** | **759** | **95** | **95** | **949** |

三个子集的分工：

- **train（759 张）**：参与训练，是模型学习目标特征的来源；
- **val（95 张）**：训练过程中每轮用于评估指标、早停判断与挑选最优权重；
- **test（95 张）**：**全程不参与训练、验证和调参**，只留到最后用于模拟"新图片检测"（Level 4）。

图片统一按 `类别_四位序号.jpg` 重命名（如 `obstacle_0129.jpg`），对应的 YOLO 标签使用**同名 `.txt`**（如 `obstacle_0129.txt`）。每张图的原始文件名、宽高、格式和 sha256 都记录在 `reports/image_inventory.csv` 中，便于追溯核对。

> **一个需要注意的点**：标签与图片是靠**文件名**配对的，而文件名由上述划分过程生成。因此只要原始图片有增删，编号就会整体错位，导致标签静默配到错误的图片上（`validate_labels.py` 只检查格式，发现不了这种错位）。所以划分脚本在标注完成后**不应再重跑**；如需重跑，必须先备份 `dataset/labels/`。

## 四、目标标注

### 1. 标注工具与启动方式

使用 **LabelImg 1.8.6**（Python + PyQt5 图形界面）完成标注，安装在同一个虚拟环境中。选择它的原因：

- 直接输出 **YOLO 格式的 `.txt`**，不需要额外的 XML→TXT 格式转换；
- 支持通过**预定义类别文件**固定类别列表，避免每次手动输入类别名；
- 轻量，一条命令即可启动。

启动通过项目根目录的 `label-*.cmd` 脚本完成，脚本自动处理了三件事：

1. **设置 Qt 插件路径**（`QT_PLUGIN_PATH` 等）。项目路径含中文，若不做设置 LabelImg 会因找不到 Qt 平台插件而启动失败；
2. 依次传入**图片目录**、**类别文件**、**标签保存目录**三个参数，避免每次手动在界面上切换目录；
3. 先运行 `build_annotation_queue.py` 生成待标注队列——该脚本把**尚未标注的图片**挑出来放进 `.annotation_queue/` 工作目录，这样标注时不必在几百张图里自己找哪些还没标，标完一张队列里就少一张需要关注的图。

标注时的操作：按 `W` 开始画框，拖动矩形，按类别快捷键选择类别，按 `D` 切换到下一张，按 `Ctrl+S` 保存。**标签保存位置由启动参数决定，不要在界面上手动修改"保存目录"。**

### 2. 类别编号与固定顺序

三个类别及其编号，由 `predefined_classes.txt` 固定顺序：

```text
0 obstacle    障碍物
1 cola        可乐罐
2 football    足球
```

这一点必须与 `data.yaml` 中的 `names` 完全一致：

```yaml
names:
  0: obstacle
  1: cola
  2: football
```

> **为什么强调这个顺序**：YOLO 标签文件里存的是**类别编号**而不是类别名。如果标注时的类别顺序和训练配置里的顺序不一致，标签中的 `0/1/2` 就会指向错误的类别——模型会把"可乐罐"学成"障碍物"。标注前必须先确认两处一致。

### 3. YOLO 标签格式

每张参与训练的图片对应一个**同名的 `.txt` 文件**（如 `obstacle_0001.jpg` ↔ `obstacle_0001.txt`），文件中**每行描述一个目标框**，共 5 个字段：

```text
0 0.664062 0.687500 0.587500 0.575000
│     │        │        │        └── 框高 ÷ 图片高
│     │        │        └─────────── 框宽 ÷ 图片宽
│     │        └──────────────────── 框中心 y ÷ 图片高
│     └───────────────────────────── 框中心 x ÷ 图片宽
└─────────────────────────────────── 类别编号
```

后四个数值都是**归一化到 0~1 的比例**（相对于图片宽高），而不是像素坐标。以 `obstacle_0001.jpg`（640×480）为例换算回像素：

```text
中心 x = 0.664062 × 640 = 425 px      框宽 = 0.587500 × 640 = 376 px
中心 y = 0.687500 × 480 = 330 px      框高 = 0.575000 × 480 = 276 px

左上角 = (425 − 376/2, 330 − 276/2) = (237, 192)
右下角 = (425 + 376/2, 330 + 276/2) = (613, 468)
```

即该障碍物占据画面约 **59% 宽度、58% 高度**，是一个大目标——这与第六节中 obstacle 类召回率达到 1.000 的现象一致。

**使用归一化坐标的好处**：标签与图片的实际分辨率无关。本项目原始图片存在 640×480 和 640×400 两种尺寸，归一化标签可以通用；若换成像素坐标，就必须为每种分辨率分别标注。

另外三个类别的真实标签样例（均取自训练集）：

```text
obstacle_0001.txt    0 0.664062 0.687500 0.587500 0.575000     # 大目标，占画面约 59% 宽
cola_0001.txt        1 0.153906 0.527083 0.085938 0.345833     # 细长小目标，占画面约 9% 宽
football_0001.txt    2 0.430469 0.577083 0.167187 0.200000     # 中等目标，占画面约 17% 宽
```

### 5. 标注质量检查

标注完成后、开始训练前，用 `validate_labels.py` 做强制校验，检查四项内容：

1. **每张图片是否有对应的标签文件**（缺标签的图片会在训练时被当作"背景图"，使模型学到"这里没有目标"）；
2. 每行是否恰好 **5 个字段**；
3. **类别编号**是否在 `0/1/2` 范围内；
4. **坐标**是否都落在 0~1 之间，且宽高大于 0。

校验通过输出：

```text
检查通过，共检查 854 个目标框。
```

> **为什么这一步不能跳过**：Ultralytics 会把没有标签文件的图片当作**背景图**参与训练。如果某类图片缺失标签而直接开训，模型会被明确地教成"这类场景中没有任何目标"，导致该类别几乎无法被检出，而且这种错误在训练日志里不会有任何报错——只能靠训练前的数据校验拦住。

### 6. 标注过程中的问题与反思

1. **42 个标签因文件名与类别编号错误而失效**：早期曾把原始图片目录直接拖入 LabelImg 标注，标签按原始文件名（`image_rgb_*.txt`）保存，且类别全部落在第一项（obstacle）。这些文件与重命名后的数据集无法对应，已用 `clean_obsolete_labels.py` 按 sha256 逐一比对确认后安全清理（详见第七节 7.1）。

2. **标注规则需要统一并提前明确**：本项目最终 854 个标签全部是"每张图 1 个框"，即采用"只标画面主目标"的策略。而第六节发现测试集上有 5 张图被模型多检出第二个框——如果那些画面中确实存在次要目标而未标注，就会给模型传递矛盾的监督信号（同类场景有时算背景、有时算目标），从而拉低 Precision。**教训是：标注规则应在开工前一次性定死，并在整个数据集上严格执行。**

## 五、模型训练

### 1. 基础模型与参数选择

采用 **Ultralytics YOLO11n** 作为基础模型，从官方 COCO 预训练权重 `yolo11n.pt` 出发做**迁移学习**——训练日志中的 `Transferred 448/499 items from pretrained weights` 表明从预训练权重继承了 448 项参数，模型只需学习本项目三个类别的特征，显著减少了对数据量的需求。

模型规模：**181 层、2,590,425 个参数、6.5 GFLOPs**。

| 参数 | 取值 | 选择理由 |
|---|---|---|
| `model` | `yolo11n.pt` | YOLO11 的 nano 版本，约 259 万参数。本项目数据集规模为 854 张、类别仅 3 类，n 版容量足够；更大的 s/m 版会让显存与训练时间成倍增长，而在此数据规模下收益有限 |
| `epochs` | 100 | 数据集较小，100 轮足以收敛 |
| `imgsz` | 640 | YOLO 系列的标准输入尺寸，也是 6 GB 显存下的稳妥选择 |
| `batch` | 8 | 实测显存占用约 2.2 GB（训练日志中的 `GPU_mem 2.2G`），在 6 GB 显存下留有余量 |
| `device` | 0 | 使用第 0 号 GPU（RTX 3060 Laptop） |
| `workers` | 4 | 数据加载的并行进程数。`train.py` 中的 `if __name__ == "__main__":` 是 Windows 下多进程数据加载的必需写法 |
| `patience` | 20 | 连续 20 轮验证指标无提升即早停，避免无效训练 |
| `seed` | 3082258819 | 用学号取模固定随机种子，保证训练结果可复现（学号本身超出 numpy 允许的 2³²−1，需取模，详见第七节 7.3） |
| 其余 | 默认值 | 学习率 `lr0=0.01`、`lrf=0.01`、`warmup_epochs=3.0`、`mosaic=1.0`、`close_mosaic=10` 等均采用官方默认设置 |

### 2. 训练过程与资源占用

训练在本机 RTX 3060 Laptop（6 GB 显存）上完成，共 **100 个 epoch**，单轮耗时约 **17 秒**，显存占用稳定在 **2.2 GB**，全程未出现显存不足或 CUDA 报错。训练启用了混合精度（AMP），启动时自检通过并打印 `AMP: checks passed ✅`；最后一层 `model.23.dfl.conv.weight` 被冻结。

> 训练过程曾在第 79 轮意外中断。中断原因与处理见第七节 7.6：通过 `resume_train.py` 从 `last.pt` **断点续训**至第 100 轮，**没有从头重训**，因此最终权重仍来自同一次连续的训练过程。

## 六、验证与新图片推理

### 1. 四个指标的含义

- **Precision（精确率）**：模型报出的检测框中，真正属于该类的比例。低 P 表示**误检**多。
- **Recall（召回率）**：真实目标中被成功检出的比例。低 R 表示**漏检**多。
- **mAP50**：IoU 阈值取 0.5 时的平均精度，衡量"大致把目标框住"的能力。
- **mAP50-95**：IoU 从 0.50 到 0.95、每隔 0.05 取一个阈值（共 10 个）分别算 AP 再平均，对**边界框的贴合精度**要求严格得多，因此数值总是明显低于 mAP50。

### 2. 验证集结果

在 95 张验证集图片（每张 1 个目标）上，用最优权重 `best.pt` 得到：

| 类别 | Precision | Recall | mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|
| obstacle | 0.992 | **1.000** | 0.995 | 0.740 |
| cola | 0.957 | 0.966 | 0.962 | 0.529 |
| football | 0.997 | 0.912 | 0.976 | 0.557 |
| **全部** | **0.982** | **0.959** | **0.978** | **0.608** |

**结果分析：**

- **obstacle 表现最好**：Recall 达到 **1.000**，即 32 张障碍物验证图全部被正确检出，无一漏检。这与障碍物在画面中占比大有关（训练标签的平均宽度为 0.47），大目标的特征更显著、更易学习。
- **football 的 Recall 相对最低（0.912）**：存在少量漏检，推测与部分足球样本尺寸小或存在运动模糊有关。
- **cola 的 mAP50-95 最低（0.529）**：可乐罐在画面中仅占约 **12%** 宽度（训练标签平均宽 0.12、高 0.39），属于细长的小目标。mAP50 达到 0.962 说明"能找到它"，但 mAP50-95 偏低说明"框得不够精确"——这是数据集本身的客观难度，而非标注错误。

### 3. 训练集之外的新图片检测（Level 4）

用自己训练得到的 `best.pt`，对 **95 张测试集图片**（全程未参与训练、验证和调参）做推理，置信度阈值 0.25，结果保存在 `results/test_predictions/`。

## 七、问题与解决过程

本节按「问题现象 — 原因分析 — 解决方法 — 验证结果」记录实际遇到的问题。这些问题都是真实发生过的，解决过程中也借助了阅读官方文档与库源码。

### 7.1 标注阶段：42 个标签因文件名和类别错误而失效

- **问题现象**：`dataset/labels/train/` 下存在 42 个名为 `image_rgb_*.txt` 的标签文件，既没有同名的图片，内容中的类别编号也全是 `0`（obstacle）。这些文件对训练没有任何作用，还会干扰对数据集的判断。
- **原因分析**：早期标注时曾把**原始图片目录**直接拖入 labelImg，标签便按原始文件名（`image_rgb_20260727_094528.txt`）保存，且当时没有切换类别，全部按类别列表的第一项（obstacle）保存。后来数据集已按 `类别_序号.jpg` 重新组织并改名，这批标签与图片的命名体系脱节，成为残留数据。
- **解决方法**：编写 `clean_obsolete_labels.py`，按 sha256 逐张比对原始图片与 `dataset/images` 中的图片，确认这些标签对应的目标标签**已经存在**后才移入 `reports/label_backup/`。脚本只在"能找到同名原图 + 有唯一匹配的数据集图片 + 目标标签已存在"三个条件同时满足时才移动，任何一条不满足就保留并在报告中说明，避免误删唯一的标注来源。
- **验证结果**：42 个文件全部安全移入备份，`dataset/labels/` 下不再有与图片不匹配的标签；同时确认训练集标签数（506）、验证集（47）无变化，说明只清理了无用数据。清理明细记录在 `reports/obsolete_label_cleanup.json`。

### 7.2 环境阶段：预训练权重无法自动下载

- **问题现象**：首次执行训练时，`YOLO("yolo11n.pt")` 触发的权重自动下载长时间无响应，`curl` 报 `Failed to connect to github.com:443 after 21029 ms`，训练无法启动。
- **原因分析**：Ultralytics 的预训练权重托管在 GitHub Releases，而本机访问 GitHub 极不稳定（实测 Python `urllib` 请求 20 秒超时、`curl` 21 秒超时；同一时刻国内镜像连通正常）。训练流程的第一步就依赖这个下载，因此直接阻塞。
- **解决方法**：从可正常访问的 HuggingFace 镜像下载权重并预置到项目目录，使 `YOLO("yolo11n.pt")` 的存在性检查直接命中本地文件，不再触发联网下载。同时把 `yolo11n.pt` 加入 `.gitignore`，避免 5.4 MB 的二进制文件进入仓库。
- **验证结果**：`torch.load` 校验权重可正常加载（`DetectionModel`，`nc=80`，COCO 预训练），训练随即正常启动并打印 `Transferred 448/499 items from pretrained weights`。

### 7.3 训练启动：随机种子超出 numpy 取值范围

- **问题现象**：训练启动后立刻退出，报 `ValueError: Seed must be between 0 and 2**32 - 1`。
- **原因分析**：`train.py` 中直接用学号 `20262128003` 作为随机种子以保证实验可复现，但 numpy 要求种子落在 `0 ~ 2³²−1`（4294967295）区间内，学号约为 2.0×10¹⁰，超出约 4.7 倍，因此 `np.random.seed()` 直接抛异常。
- **解决方法**：对学号取模，既保留"用学号固定种子"的原意，又落到合法区间：`SEED = 20262128003 % (2**32)`，并在代码注释中写明原因。
- **验证结果**：修正后训练正常启动，`runs/yolo11n_3classes/args.yaml` 中记录 `seed: 3082258819`，与取模结果一致。

### 7.4 数据集配置：`data.yaml` 的相对路径依赖工作目录

- **问题现象**：从项目目录运行训练正常，但从其他目录运行时立刻失败：`FileNotFoundError: Dataset ... images not found`。
- **原因分析**：`data.yaml` 中原来写的是相对路径 `path: dataset`。查阅 Ultralytics 源码（`ultralytics/data/utils.py` 第 623–625 行）可见其解析逻辑：先按**当前工作目录**判断该相对路径是否存在，只有不存在时才回退到全局设置 `datasets_dir` 去解析。因此该配置隐式依赖"必须在项目目录内运行"，换目录即失效。而全局设置中的 `datasets_dir` 指向一个并不存在的目录，进一步放大了这个隐患。
- **解决方法**：去掉 `path:` 字段，改为 `train: dataset/images/train`、`val: dataset/images/val`。此时 Ultralytics 以 `data.yaml` 所在目录为基准解析路径，与工作目录无关；同时补建 `datasets_dir` 指向的目录，消除悬空设置。
- **验证结果**：分别在项目目录、`YOLO/` 目录和工作区根目录三个不同工作目录下调用 `check_det_dataset()`，均正确解析出 `dataset/images/train` 与 `dataset/images/val`。整个配置不含任何绝对路径，换机器同样可用。

### 7.5 AMP 自检依赖联网下载，但失败不会中断训练

- **问题现象**：训练启动阶段卡在 `AMP: downloading yolo26n.pt for AMP checks`，`curl` 反复超时重试。
- **原因分析**：Ultralytics 在启用混合精度（AMP）前会做一次数值一致性自检，需要一个 COCO 预训练的 `yolo26n.pt` 作为对照模型。该文件不随包提供，需从 GitHub 下载，而本机访问 GitHub 不稳定。阅读 `ultralytics/utils/checks.py` 第 968–1041 行确认：整段自检包在 `try` 中，下载失败会抛出 `ConnectionError` 并被 `except ConnectionError` 捕获，只打印一条 `checks skipped` 警告，随后仍执行 `return True`——**即 AMP 保持开启、训练继续**，只有数值异常（`AssertionError`）才会真正关闭 AMP。
- **解决方法**：既然失败不致命、只是白等重试，直接从镜像预置 `weights/yolo26n.pt`，使自检的存在性检查命中本地文件，完全不触发联网。
- **验证结果**：重启训练后自检瞬间通过并打印 `AMP: checks passed ✅`，训练正常开始。该文件仅用于自检（Ultralytics 自身也标注 `one-time, not used for training`），已通过 `.gitignore` 的 `/weights/` 规则排除。

### 7.6 训练中断与断点续训

- **问题现象**：训练在 epoch 79/100 处停止，`results.csv` 不再增长，且 `results.png`、混淆矩阵、P/R 曲线等收尾图表**全部缺失**（这些图在训练完全结束时才统一生成，而它们正是本项目需要提交的训练结果图）。
- **原因分析**：训练以后台任务方式启动，而我用了一条"一直等待训练结束"的长时阻塞命令来监视进度，该命令被执行环境按 600 秒上限强制终止，后台训练进程随之被一并结束。事后核对时间戳可确认：`last.pt` 的写入时间（22:40:40）与监视命令被终止的时刻完全一致。**这是一次操作方式导致的意外中断，代码与数据本身没有问题。**
- **解决方法**：新增 `resume_train.py`，从 `runs/yolo11n_3classes/weights/last.pt` 调用 `model.train(resume=True)`。`resume` 会从检查点恢复优化器状态、数据集参数与总轮数，接着第 79 轮继续训练。同时改变监视方式：只用秒级短命令查询 `results.csv`，不再使用长时阻塞命令。
- **验证结果**：续训从 epoch 80 接续，顺利跑满 100 轮，并补齐了 `results.png`、`confusion_matrix.png`、`BoxPR_curve.png`、`val_batch*_pred.jpg` 等全部收尾产物；最优权重出现在 epoch 74（P=0.982，R=0.959，mAP50=0.976，mAP50-95=0.609）。**经验教训**：训练任务不要与长时阻塞的监视命令放在同一进程链上；此外笔记本电脑在训练期间休眠也会造成大量空转（`results.csv` 累计时间曾达 6.3 小时，而每轮实际仅需约 17 秒）。

### 7.7 实验设计：短轮次训练的末期指标会虚高

- **问题现象**：为缩短训练时间，用 `epochs=20` 做了一次流程彩排。结果第 20 轮 mAP50 达到 **0.986**，既高于正式训练同期的 0.942，甚至超过 100 轮正式训练的最终值 0.978。这个"反常"结果一开始容易被误判为"短训练反而更好"。
- **原因分析**：回读两次训练的 `args.yaml` 与 `results.csv` 后定位到两点：
  1. 该次彩排的 `seed` 实际为默认值 `0`，与正式训练的 `3082258819` 不同，因此两次实验的增强与批次顺序自第 1 轮起就不同，逐轮对比本身不成立；
  2. **更本质的是，`epochs` 会连带改变两套训练日程**：其一是学习率按总轮数线性衰减（`lr0=0.01 → lrf·lr0=1e-4`），实测第 20 轮学习率分别为 **8.5×10⁻⁵ 与 1.16×10⁻³，相差 13.6 倍**；其二是 `close_mosaic=10` 的含义是"倒数 10 轮关闭 mosaic 增强"，即彩排在**第 11 轮**就关闭 mosaic（后 10 轮占全程一半，都在无增强的干净图上精调），而正式训练要到**第 91 轮**才关闭。因此短轮次训练末期相当于已进入精调阶段，指标自然偏高。
- **解决方法**：明确区分两类实验——短轮次仅用于**验证流程是否跑通**，不作为模型质量评估依据；所有正式指标一律取自 100 轮的完整训练。若需验证可复现性，应使用**完全相同的配置跑两次**再逐行比对 `results.csv`，而不是拿短轮次去比长轮次。
- **验证结果**：确认短轮次产物（`runs/detect/yolo11n_rehearsal/`）完整生成，证明流程可用；正式结果仍取自 100 轮训练。**由此形成一条工程习惯：超参数覆盖必须回读 `args.yaml` 确认实际生效值，不能只凭命令行的写法判断。**

## 八、本地图片识别页面（Level 5）

### 1. 技术选型

选用 **Streamlit 1.64.0** 搭建本地页面，理由：

- **纯 Python**，无需编写 HTML / CSS / JavaScript，可以把精力集中在"模型调用"这一核心环节；
- 内置的 `file_uploader`（上传）、`image`（显示图片）、`dataframe`（表格）、`slider`（阈值调节）四个组件，恰好覆盖本项目"上传 → 推理 → 展示"的全部需求；
- 本地运行，一条 `streamlit run app.py` 即可在浏览器打开，便于截图与录屏。

### 2. 依赖安装前的安全性验证

Streamlit 会引入 22 个新依赖包（`pandas`、`pyarrow`、`altair`、`protobuf`、`uvicorn` 等）。由于本项目环境中的 `torch 2.7.1+cu118` 与 CUDA 组合安装成本较高，**安装前先做了试算**：

```powershell
python -m pip install streamlit --dry-run -i https://pypi.tuna.tsinghua.edu.cn/simple
```

试算确认这 22 个包与现有环境**互不冲突**，且不会改动 `torch`、`torchvision`、`numpy`、`pillow`、`opencv` 等已装包。安装后再执行 `pip check` 复核，结果为 `No broken requirements found`，四个核心包版本全部保持不变。

> 这一步的意义在于：**不能为了装一个页面框架而破坏已经验证过的训练环境**。先试算、再安装、装完复核版本，是这个环节应有的做法。

### 3. 实现流程

```text
打开本地页面（streamlit run app.py）
    ↓  用户在页面上选择并上传一张本地图片
    ↓  后端加载自己训练得到的 runs/yolo11n_3classes/weights/best.pt
    ↓  调用 model.predict() 完成目标检测
    ↓  页面显示：原始图片 + 检测结果图（目标框 / 类别名 / 置信度）
    ↓  表格列出每个目标框的类别与置信度数值
```

### 4. 三个关键技术点

1. **模型只能加载一次**：Streamlit 的运行机制是"每次交互都从头重跑整个脚本"。若不加处理，用户每拖动一次置信度滑块都会重新加载一遍权重文件，页面会明显卡顿。因此用 `@st.cache_resource` 装饰加载函数，使模型首次加载后常驻内存。

2. **BGR 与 RGB 的通道顺序**：`result.plot()` 返回的是 OpenCV 风格的 **BGR** 顺序图像，直接交给 `st.image` 显示会导致**红蓝通道颠倒**（整张图色调错误、框的颜色也不对）。必须先用 `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)` 转换。

3. **向模型传 PIL 对象而不是 numpy 数组**：Ultralytics 对**裸 numpy 数组按 BGR 解释**（遵循 OpenCV 惯例），而 PIL 图像会按 RGB 正确处理。因此代码中传入的是 `Image.open(...).convert("RGB")` 得到的 PIL 对象，避免输入通道顺序错误导致检测异常。

### 5. 页面功能与验证结果

页面提供的功能：

- 顶部显示**当前实际加载的权重路径**（`runs/yolo11n_3classes/weights/best.pt`），可直接证明调用的是本项目自己训练的模型，而不是通用预训练模型；
- 置信度阈值滑块（0.05 ~ 0.95，默认 0.25），可实时调整；
- 图片上传入口；
- 左右并排显示原始图片与检测结果图；
- 表格列出每个目标框的类别、置信度与像素坐标（左上角 / 右下角）。

**一致性验证**：为确认页面输出与批量推理（`predict.py`）完全一致，对同一张测试图做了逐项比对：

| 项目 | 页面输出 | `predict.py` 输出 |
|---|---|---|
| 类别 | football | football |
| 置信度 | 0.8427 | 0.8427 |
| 左上角坐标 | 128, 187 | 128, 187 |
